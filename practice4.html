GPU Architecture & Hardware

Before writing a single line of graphics code, you must understand what happens inside the silicon when you call glVertex3f().

🔧 The Graphics Processing Unit (GPU)

A GPU is fundamentally different from a CPU. While a CPU has 4-32 powerful cores optimized for sequential tasks, a GPU has thousands of simpler cores designed for parallel execution.

Why This Architecture?

When rendering a 1920×1080 image, you need to process 2,073,600 pixels. Each pixel's color calculation is independent of others. A GPU exploits this "embarrassing parallelism" by running thousands of pixel shaders simultaneously.

⚡ From Electrons to Pixels

Here's what happens when you call glutSwapBuffers():

  1. Command Buffer: Your OpenGL calls are translated into GPU commands and stored in a command buffer in VRAM
  2. Front Buffer Display: The GPU's Display Controller reads the front buffer at 60-360Hz via HDMI/DisplayPort
  3. RAMDAC/Digital Encoder: Converts digital pixel values to analog signals (or keeps digital for HDMI/DP)
  4. Electron Gun (CRT) / Liquid Crystal (LCD): Physical display technology activates
  5. Photon Emission: Light travels to your retina at ~3×10⁸ m/s
Pixel Clock = H_Res × V_Res × Refresh_Rate × Overscan_Factor

For 1920×1080 @ 60Hz: 1920 × 1080 × 60 × 1.05 ≈ 130 MHz pixel clock

🔧 Stage 1: Vertex Processing (Hardware)

When you call glVertex3f(x, y, z), this vertex enters the GPU's Vertex Fetch Unit. The GPU reads vertex attributes from VRAM through the L2 cache.

What Happens in Silicon:

  • Input Assembler: Groups vertices into primitives (points, lines, triangles)
  • Vertex Shader Execution: Each vertex runs on a separate SIMD lane in the SM (Streaming Multiprocessor)
  • Register Allocation: The shader compiler determines how many registers each vertex shader needs
  • Occupancy: More registers = fewer concurrent vertices = lower performance
GPU Occupancy = (Active Warps per SM) / (Max Warps per SM) × 100%

⚡ Stage 5: Rasterization (Physics of Light)

Rasterization is where 3D triangles become 2D pixels. This stage is fixed-function hardware — you can't program it with shaders.

The Scanline Algorithm (Hardware Implementation):

  1. Compute bounding box of triangle in screen space
  2. For each pixel in bounding box, test if center is inside triangle using barycentric coordinates
  3. Interpolate vertex attributes (color, texture coords, depth) across the triangle
  4. Generate a "fragment" for each covered pixel
Barycentric: P = αA + βB + γC, where α + β + γ = 1 and α,β,γ ≥ 0

Hardware Implementation: Modern GPUs use tile-based rasterization. The screen is divided into 8×8 or 16×16 pixel tiles. Each tile is processed independently, keeping all data in fast on-chip memory.

Linear Algebra for Graphics

Computer graphics is essentially applied linear algebra. Every vertex, every transformation, every lighting calculation uses vectors and matrices.

📐 Vectors: Direction and Magnitude

A vector v = (x, y, z) represents both a direction and magnitude in 3D space. In graphics, vectors represent:

  • Positions: Where a vertex is in space
  • Directions: Surface normals, light directions, view directions
  • Colors: RGB values as a 3D vector

Essential Vector Operations

Dot Product: a · b = |a||b|cos(θ) = aₓbₓ + aᵧbᵧ + a₂b₂

Physical Meaning: The dot product tells you how much two vectors point in the same direction. When lighting a surface, N · L (normal dot light direction) gives the intensity of diffuse reflection. If the light is directly overhead (N and L parallel), cos(0°) = 1 → maximum brightness. If the light is at 90°, cos(90°) = 0 → no diffuse light.

Cross Product: a × b = (aᵧb₂ - a₂bᵧ, a₂bₓ - aₓb₂, aₓbᵧ - aᵧbₓ)

Physical Meaning: The cross product produces a vector perpendicular to both inputs. In graphics, this is used to generate surface normals from two tangent vectors. If you have a triangle with edges e1 and e2, the normal is normalize(cross(e1, e2)).

Matrices: The Language of Transformation

In 3D graphics, we use 4×4 matrices because they can represent both linear transformations (rotation, scale) AND translation in a single multiplication.

📐 Why 4×4 Matrices? (Homogeneous Coordinates)

A 3×3 matrix can rotate and scale, but it CANNOT translate (move) a point. Translation requires adding a vector, which is an affine operation, not linear.

By adding a 4th coordinate (w=1 for points, w=0 for vectors), we can encode translation in the matrix:

┌ ┐ ┌ ┐ ┌ ┐
│ m11 m12 m13 tx │ │ x │ │ m11x+m12y+m13z+tx │
│ m21 m22 m23 ty │ × │ y │ = │ m21x+m22y+m23z+ty │
│ m31 m32 m33 tz │ │ z │ │ m31x+m32y+m33z+tz │
│ 0 0 0 1 │ │ 1 │ │ 1 │
└ ┘ └ ┘ └ ┘

Key insight: When w=1, the translation components (tx, ty, tz) are added. When w=0, they are not — this is why direction vectors shouldn't be translated!

The Transformation Pipeline

Every vertex goes through three transformations before reaching the screen:

  1. Model Matrix (M): Object space → World space (position, rotate, scale the object)
  2. View Matrix (V): World space → Camera space (move the world so camera is at origin)
  3. Projection Matrix (P): Camera space → Clip space (perspective or orthographic)
v_clip = P × V × M × v_local = MVP × v_local

Note: Matrix multiplication is applied RIGHT TO LEFT. The local vertex is transformed first by M, then V, then P.

┌ ┐

Why this works: A point (x, y) rotated by angle θ becomes (x·cosθ - y·sinθ, x·sinθ + y·cosθ). This is exactly what the matrix multiplication does. The Z coordinate stays the same because we're rotating around the Z axis.

Perspective Projection

Perspective projection makes distant objects smaller — this is how our eyes work.

📐 Perspective Division (The Magic of w)

After multiplying by the projection matrix, we get a 4D vector (x, y, z, w). The GPU then performs perspective division:

x_ndc = x_clip / w_clip, y_ndc = y_clip / w_clip, z_ndc = z_clip / w_clip

Why this creates perspective: The projection matrix sets w_clip = -z_eye (the negative eye-space Z coordinate). Objects farther away (larger z) get a larger w, so after division by w, they become smaller in NDC space!

This is the mathematical trick that makes 3D graphics work. The 4th coordinate isn't just "extra data" — it's the key to perspective.

Light, Color & Physics

Rendering realistic images requires understanding how light behaves in the real world. This section covers the physics that drives computer graphics algorithms.

⚡ The Electromagnetic Spectrum

Light is an electromagnetic wave. The visible spectrum ranges from approximately 380nm (violet) to 700nm (red).

Your monitor doesn't emit "light" in the physical sense — it emits photons at three specific wavelengths (red ~610nm, green ~530nm, blue ~460nm). Your brain interpolates these to perceive millions of colors.

Why RGB?

Human eyes have three types of cone cells (S, M, L) sensitive to short, medium, and long wavelengths. RGB display technology exploits this trichromatic nature. However, RGB cannot reproduce all colors visible to the human eye — some highly saturated greens and cyans are impossible on standard displays.

The Phong Reflection Model

The Phong model is the foundation of real-time lighting. It breaks reflection into three components:

⚡ Phong Lighting Equation

I = I_ambient + I_diffuse + I_specular + I_emissive

Where:

  • Ambient (Iₐ): Constant "background" light. Simulates indirect lighting (light bouncing off walls, ceiling, etc.). In reality, ambient light is the result of complex global illumination, but we approximate it as a constant.
  • Diffuse (Iₐ): Light scattered equally in all directions by a rough surface. Follows Lambert's cosine law: Iₐ = kₐ × (N · L) × I_light. The dot product N·L represents the cosine of the angle between surface normal and light direction.
  • Specular (Iₛ): Mirror-like reflection. Iₛ = kₛ × (R · V)^shininess × I_light. The shininess exponent controls how "tight" the highlight is. Higher values = shinier surface (metal, plastic).
  • Emissive (Iₑ): Light emitted by the object itself (glowing objects).

Reflection Vectors

📐 Computing the Reflection Vector R

Given light direction L and surface normal N, the perfect reflection direction R is:

R = 2(N · L)N - L

Derivation: Decompose L into components parallel and perpendicular to N. The parallel component is (N·L)N. The perpendicular component is L - (N·L)N. Reflection flips the perpendicular component: R = (N·L)N - (L - (N·L)N) = 2(N·L)N - L.

Optimization: Instead of computing R and then R·V, use the halfway vector H = normalize(L + V). Then specular = (N · H)^shininess. This is cheaper and gives slightly different but acceptable results (Blinn-Phong model).

🔧 Double Buffering Deep Dive

When you use GLUT_DOUBLE, FreeGLUT requests two framebuffer regions from the GPU:

  • Front Buffer: Currently being scanned out to the display by the GPU's Display Controller
  • Back Buffer: Where your rendering commands draw

glutSwapBuffers() swaps the pointers. The GPU's display controller has a register that points to the front buffer. Swapping just updates this pointer — no memory copy!

Triple Buffering: Some drivers support triple buffering (3 buffers) to reduce stuttering. FreeGLUT doesn't directly control this, but you can enable it via driver settings.

C++

// Basic 2D rendering (no depth needed)

// 3D with transparency and anti-aliasing
glutInitDisplayMode(GLUT_DOUBLE | GLUT_RGBA | GLUT_DEPTH | GLUT_ALPHA | GLUT_MULTISAMPLE);

// Full-featured: depth, stencil, accumulation, alpha

🔧 Context Switching Cost

Switching windows means switching OpenGL contexts. On the GPU, this may require:

  • Flushing the current command buffer
  • Reloading context-specific state (viewport, scissor, bound buffers)
  • Invalidating some GPU caches

Performance Tip: Minimize context switches. If rendering to multiple windows, batch operations per window rather than switching back and forth.

🔧 Fullscreen vs Borderless Windowed

True fullscreen (what FreeGLUT does) gives the application exclusive control of the display:

  • Advantages: Lowest latency (no compositor), maximum performance, can change display mode
  • Disadvantages: Alt-Tab is slower, OS notifications may not show

Modern games often use "borderless windowed" mode instead, which looks like fullscreen but is actually a window covering the entire screen. FreeGLUT doesn't directly support this — you'd need platform-specific code.

Callbacks & Event Processing

FreeGLUT is an event-driven library. You register callback functions, and FreeGLUT calls them when events occur. This is fundamentally different from a game loop where you poll for input.

glutMainLoop
void glutMainLoop(void);

Description: Enters the FreeGLUT event processing loop. This function NEVER RETURNS in standard GLUT. In FreeGLUT, it can return if GLUT_ACTION_ON_WINDOW_CLOSE is set appropriately and glutLeaveMainLoop is called.

🔧 What Happens Inside glutMainLoop

The event loop is the heart of any GUI application. Here's what FreeGLUT does on each iteration:

  1. Check for OS events: Poll the OS message queue (Windows: PeekMessage, X11: XPending)
  2. Process input events: Mouse moves, key presses, window resizes → call registered callbacks
  3. Call idle callback: If no events and glutIdleFunc is registered
  4. Call timer callbacks: Check if any registered timers have expired
  5. Call display callbacks: For windows that have been marked for redisplay via glutPostRedisplay
  6. Swap buffers: If double-buffered, swap front/back buffers
  7. Repeat: Go back to step 1
⚠️ Critical: Never put heavy computation directly in a callback. The event loop must remain responsive. For game logic, use glutTimerFunc with a fixed timestep instead of glutIdleFunc.
glutMainLoopEvent
void glutMainLoopEvent(void);

Description: (FreeGLUT only) Processes a SINGLE iteration of the event loop. This allows you to integrate FreeGLUT into your own loop structure.

C++
// Custom game loop with FreeGLUT
void gameLoop() {
    while (running) {
        // Process one FreeGLUT event iteration
        glutMainLoopEvent();

        // Your own fixed-timestep physics
        while (accumulator >= dt) {
            updatePhysics(dt);
            accumulator -= dt;
        }

        // Render
        glutPostRedisplay();

        // Frame rate limiting
        sleep(1); // Platform-specific
    }
}

Display Control Functions

These functions control what appears on screen, when buffers are swapped, and synchronization with the display.

glutSwapBuffers
void glutSwapBuffers(void);

Description: Swaps the front and back buffers of the current window. Only valid when using GLUT_DOUBLE.

🔧 The Swap Operation (Hardware Level)

When you call glutSwapBuffers(), here's what happens in hardware:

  1. Command Buffer Flush: All pending OpenGL commands are sent to the GPU
  2. Wait for V-Blank (if V-Sync on): The GPU waits for the display's vertical blanking interval
  3. Pointer Swap: The GPU's display controller register is updated to point to the back buffer
  4. Old front buffer becomes back buffer: Ready for the next frame's rendering

Buffer Address Registers: Modern GPUs have hardware registers that store the physical memory address of the front buffer. Swapping is literally a single register write — nanoseconds!

⚡ V-Sync and Screen Tearing

Without V-Sync, the GPU may swap buffers while the display is mid-scan. This causes screen tearing — the top half shows the old frame, the bottom half shows the new frame.

V-Sync forces the swap to happen during the vertical blanking interval — the brief period when the electron beam (CRT) or row drivers (LCD) reset from bottom to top. At 60Hz, this happens 60 times per second, with ~16.67ms between frames.

🔧 How Bitmap Fonts Work

Bitmap fonts are stored as arrays of pixel data in FreeGLUT's memory. When rendering:

  1. FreeGLUT looks up the character in the font's glyph table
  2. Each glyph is a small bitmap (e.g., 8×13 pixels)
  3. The bitmap is uploaded to the GPU using glBitmap — a legacy OpenGL function that draws pixel rectangles
  4. glBitmap updates the raster position automatically for the next character

Performance: Each character is a separate OpenGL call. For large amounts of text, use texture atlases (modern approach) instead.

    glPushMatrix();
    glLoadIdentity();
    gluOrtho2D(0, glutGet(GLUT_WINDOW_WIDTH), 
               0, glutGet(GLUT_WINDOW_HEIGHT));

    glMatrixMode(GL_MODELVIEW);
    glPushMatrix();

    glDisable(GL_LIGHTING);
    glDisable(GL_DEPTH_TEST);

    // Set text color

}

FreeGLUT is a windowing toolkit — it creates windows and handles input. The actual rendering is done by OpenGL. This section covers the essential OpenGL concepts you need alongside FreeGLUT.

Coordinate Systems

⚡ OpenGL Coordinate Conventions

Understanding coordinate systems is fundamental:

  • Normalized Device Coordinates (NDC): After projection, x, y, z are all in [-1, 1]. The GPU clips anything outside this range.
  • Window Coordinates: NDC is mapped to actual pixel coordinates. (0,0) is the bottom-left of the viewport, NOT top-left like most 2D APIs.
  • Depth Range: After projection, z is in [-1, 1]. The depth buffer stores this as [0, 1], where 0 = near plane, 1 = far plane (with default glDepthRange).
⚠️ Common Bug: Many developers assume (0,0) is top-left. In OpenGL, (0,0) is bottom-left. When loading textures from image files (which are typically top-left origin), you may need to flip the Y coordinate or use glPixelZoom(1, -1).

3D Transformations

Transformations move, rotate, and scale objects in 3D space. In legacy OpenGL, these are done with matrix stack operations.

The Matrix Stack

OpenGL maintains two matrix stacks: GL_MODELVIEW (object-to-camera transformation) and GL_PROJECTION (camera-to-screen transformation).

glMatrixMode / glLoadIdentity / glPushMatrix / glPopMatrix
void glMatrixMode(GLenum mode);
void glLoadIdentity(void);
void glPushMatrix(void);
void glPopMatrix(void);

Description: glMatrixMode selects which matrix stack to operate on. glLoadIdentity resets to the identity matrix. glPushMatrix saves the current matrix, glPopMatrix restores it.

🔧 Matrix Stack in Hardware

The matrix stack is maintained by the OpenGL driver, not directly by the GPU. Each glPushMatrix copies the current 4×4 matrix (16 floats = 64 bytes) to a stack in CPU/driver memory. For deep hierarchies (e.g., skeleton animation with 100 bones), this can be a performance bottleneck. Modern OpenGL uses uniform buffers instead.

glTranslatef / glRotatef / glScalef
void glTranslatef(GLfloat x, GLfloat y, GLfloat z);
void glRotatef(GLfloat angle, GLfloat x, GLfloat y, GLfloat z);
void glScalef(GLfloat x, GLfloat y, GLfloat z);

Description: Multiply the current matrix by translation, rotation, or scale matrices. Operations are applied right-to-left in the code.

📐 Order Matters!

In OpenGL, transformations are post-multiplied. The code:

glTranslatef(1,0,0); glRotatef(90,0,1,0);

Produces: M_final = M_current × Translate × Rotate

This means: Rotate first, then translate. The object rotates around its own origin, then moves to (1,0,0).

If you reverse the order:

glRotatef(90,0,1,0); glTranslatef(1,0,0);

This means: Translate first, then rotate. The object moves to (1,0,0), then rotates around the world origin — orbiting in a circle!

gluLookAt
void gluLookAt(GLdouble eyeX, GLdouble eyeY, GLdouble eyeZ, GLdouble centerX, GLdouble centerY, GLdouble centerZ, GLdouble upX, GLdouble upY, GLdouble upZ);

Description: Defines the camera/view transformation. Places the camera at eye, looking at center, with up vector defining the camera's upward direction.

📐 How gluLookAt Works

Internally, gluLookAt computes:

  1. Forward vector (F): normalize(center - eye) — where the camera looks
  2. Side vector (S): normalize(cross(F, up)) — camera's right direction
  3. Up vector (U): cross(S, F) — true up (may differ from input if input wasn't perpendicular)

Then constructs the view matrix:

┌ ┐
│ Sₓ Sᵧ S₂ -dot(S, eye) │
│ Uₓ Uᵧ U₂ -dot(U, eye) │
│ -Fₓ -Fᵧ -F₂ dot(F, eye) │
│ 0 0 0 1 │
└ ┘

The negative signs on F create a right-handed coordinate system where -Z is forward in camera space.

gluPerspective / glOrtho
void gluPerspective(GLdouble fovy, GLdouble aspect, GLdouble zNear, GLdouble zFar);
void glOrtho(GLdouble left, GLdouble right, GLdouble bottom, GLdouble top, GLdouble zNear, GLdouble zFar);

Description: gluPerspective creates a perspective projection matrix (objects farther away appear smaller). glOrtho creates an orthographic projection (parallel lines stay parallel, no perspective).

📐 Perspective Matrix Derivation

Perspective projection maps the view frustum to the NDC cube [-1,1]³. The key insight is that x and y must be divided by z to create perspective:

x_ndc = (x_eye / z_eye) × (1/tan(fovy/2)) × aspect
y_ndc = (y_eye / z_eye) × (1/tan(fovy/2))

In homogeneous coordinates, division by z is achieved by setting w = -z_eye. After matrix multiplication, the GPU performs perspective division (x/w, y/w, z/w).

⚠️ zNear must be > 0: Setting zNear to 0 causes division by zero in the projection matrix. Setting zNear too small (e.g., 0.001) causes z-fighting — depth buffer precision issues where surfaces flicker because their depth values are too close together.

⚡ Light Attenuation Physics

Real light follows the inverse-square law: intensity ∝ 1/d². In OpenGL, attenuation is:

attenuation = 1 / (k_c + k_l × d + k_q × d²)

Where d is distance from light to surface. For realistic falloff:

  • k_c = 1.0 (always present)
  • k_l = 0.0 (no linear falloff)
  • k_q = 0.0 (no quadratic falloff) → no attenuation (directional/ambient-like)
  • k_q = 0.001 to 0.1 → realistic point light falloff

Texture Mapping

Texture mapping applies images to 3D surfaces. This is what makes 3D graphics look realistic — from brick walls to character skins.

How Texture Mapping Works

🔧 GPU Texture Pipeline

When a fragment shader samples a texture, the GPU performs these operations in hardware:

  1. Texture Coordinate Generation: The vertex shader outputs UV coordinates (usually in [0,1] range)
  2. Coordinate Interpolation: The rasterizer interpolates UVs across the triangle (perspective-correct interpolation)
  3. Address Calculation: The Texture Mapping Unit (TMU) converts UV to texel coordinates: u_pixel = u × width, v_pixel = v × height
  4. Wrapping: If coordinates are outside [0,1], apply wrap mode (repeat, clamp, mirror)
  5. Filtering: Apply minification/magnification filter (nearest, linear, mipmap)
  6. Memory Fetch: The TMU fetches texel data from VRAM through the texture cache
  7. Color Return: The sampled color is returned to the fragment shader

Texture Cache: GPUs have dedicated texture caches (L1 texture cache, typically 12-48 KB per SM) optimized for 2D spatial locality. This is why texture access patterns matter — random access is much slower than coherent access.

⚡ Filtering Physics

Nearest: Takes the closest texel. Fast but blocky (pixelated).

Linear (Bilinear): Samples 4 nearest texels and interpolates. Smoother but can blur details.

Mipmapping: Pre-computed smaller versions of the texture. When a texture is far away (small on screen), the GPU uses a smaller mipmap. This:

  • Reduces aliasing (shimmering/moire patterns)
  • Improves cache locality (smaller textures fit better in cache)
  • Increases memory usage by ~33%

Trilinear filtering (GL_LINEAR_MIPMAP_LINEAR): Interpolates between TWO mipmap levels AND bilinearly within each. Best quality, slightly more expensive.

Anisotropic filtering: When viewing a surface at a grazing angle (e.g., floor stretching into distance), standard mipmapping becomes blurry. Anisotropic filtering samples the texture in an elongated pattern aligned with the screen projection, preserving detail.

GLuint loadTexture(const char* filename) {
    int width, height, channels;
    unsigned char* data = stbi_load(filename, &width, &height, &channels, 0);
    if (!data) {
        printf("Failed to load texture: %s
", filename);
        return 0;
    }

    GLuint textureID;
    glGenTextures(1, &textureID);
    glBindTexture(GL_TEXTURE_2D, textureID);

    // Determine format based on channels
    GLenum format = (channels == 4) ? GL_RGBA : GL_RGB;

    // Upload texture data to GPU
    glTexImage2D(GL_TEXTURE_2D, 0, format, width, height, 
                   0, format, GL_UNSIGNED_BYTE, data);

    // Generate mipmaps automatically
    glGenerateMipmap(GL_TEXTURE_2D);

    // Set texture parameters
    glTexParameteri(GL_TEXTURE_2D, GL_TEXTURE_MIN_FILTER, 
                    GL_LINEAR_MIPMAP_LINEAR);  // Trilinear
    glTexParameteri(GL_TEXTURE_2D, GL_TEXTURE_MAG_FILTER, 
                    GL_LINEAR);               // Bilinear for magnification
    glTexParameteri(GL_TEXTURE_2D, GL_TEXTURE_WRAP_S, 
                    GL_REPEAT);
    glTexParameteri(GL_TEXTURE_2D, GL_TEXTURE_WRAP_T, 
                    GL_REPEAT);

    // Anisotropic filtering (if supported)
    GLfloat maxAniso;
    glGetFloatv(GL_MAX_TEXTURE_MAX_ANISOTROPY_EXT, &maxAniso);
    glTexParameterf(GL_TEXTURE_2D, GL_TEXTURE_MAX_ANISOTROPY_EXT, 
                    maxAniso);

    stbi_image_free(data);  // Free CPU memory
    return textureID;
}

🔧 Shader Execution on GPU

Shaders are compiled to GPU machine code by the driver. Here's how they execute:

  1. Compilation: GLSL source → Intermediate Representation (SPIR-V on Vulkan, driver-specific IR on OpenGL) → GPU machine code
  2. Dispatch: The GPU scheduler groups vertices/fragments into "warps" (NVIDIA: 32 threads, AMD: 64 threads)
  3. SIMD Execution: All threads in a warp execute the same instruction simultaneously on different data (SIMD — Single Instruction, Multiple Data)
  4. Divergence Penalty: If threads in a warp take different branches (if-else), the GPU must execute BOTH paths, masking inactive threads. This is why flat shading is faster than per-pixel branching.
  5. Memory Access: Fragment shaders access textures through the TMU. Coherent access patterns (neighboring pixels sampling neighboring texels) maximize cache hit rates.

Complete Shader Program Example

GLSL Vertex Shader
#version 330 core

// Input: vertex attributes from VAO
layout(location = 0) in vec3 aPos;
layout(location = 1) in vec3 aNormal;
layout(location = 2) in vec2 aTexCoord;

// Output: passed to fragment shader
out vec3 FragPos;
out vec3 Normal;
out vec2 TexCoord;

// Uniforms: constant for all vertices in draw call
uniform mat4 model;
uniform mat4 view;
uniform mat4 projection;

void main() {
    // Transform vertex to world space
    FragPos = vec3(model * vec4(aPos, 1.0));

    // Transform normal (use inverse transpose for non-uniform scale)
    Normal = mat3(transpose(inverse(model))) * aNormal;

    // Pass through texture coordinates
    TexCoord = aTexCoord;

    // Final position: Model → View → Projection → Perspective Divide
    gl_Position = projection * view * vec4(FragPos, 1.0);
}
GLSL Fragment Shader
#version 330 core

// Input: interpolated from vertex shader
in vec3 FragPos;
in vec3 Normal;
in vec2 TexCoord;

// Output: final color
out vec4 FragColor;

// Uniforms
uniform vec3 lightPos;
uniform vec3 viewPos;
uniform vec3 lightColor;
uniform sampler2D texture1;

void main() {
    // Sample texture
    vec4 texColor = texture(texture1, TexCoord);

    // Ambient
    float ambientStrength = 0.1;
    vec3 ambient = ambientStrength * lightColor;

    // Diffuse
    vec3 norm = normalize(Normal);
    vec3 lightDir = normalize(lightPos - FragPos);
    float diff = max(dot(norm, lightDir), 0.0);
    vec3 diffuse = diff * lightColor;

    // Specular (Blinn-Phong)
    vec3 viewDir = normalize(viewPos - FragPos);
    vec3 halfwayDir = normalize(lightDir + viewDir);
    float spec = pow(max(dot(norm, halfwayDir), 0.0), 32.0);
    vec3 specular = spec * lightColor;

    // Combine
    vec3 result = (ambient + diffuse + specular) * texColor.rgb;
    FragColor = vec4(result, texColor.a);
}

GLuint createShaderProgram(const char* vertexSource, 
                           const char* fragmentSource) {
    GLuint vertexShader = compileShader(vertexSource, GL_VERTEX_SHADER);
    GLuint fragmentShader = compileShader(fragmentSource, GL_FRAGMENT_SHADER);

    GLuint program = glCreateProgram();
    glAttachShader(program, vertexShader);
    glAttachShader(program, fragmentShader);
    glLinkProgram(program);

    // Check linking
    GLint success;
    glGetProgramiv(program, GL_LINK_STATUS, &success);
    if (!success) {
        char infoLog[512];
        glGetProgramInfoLog(program, 512, NULL, infoLog);
        printf("Program linking failed: %s
", infoLog);
    }

    // Shaders can be deleted after linking (they're copied into the program)
    glDeleteShader(vertexShader);
    glDeleteShader(fragmentShader);

    return program;
}

Vertex Array Objects (VAO) & Vertex Buffer Objects (VBO)

🔧 Why VBOs Are Faster Than Immediate Mode

In legacy OpenGL (glBegin/glEnd), every vertex triggers a function call and data transfer from CPU to GPU. With VBOs:

  1. Upload all vertex data to GPU VRAM ONCE
  2. Store vertex layout in VAO (which attributes, offsets, strides)
  3. Render with a single glDrawArrays call — the GPU reads directly from VRAM

Performance comparison: Immediate mode: 1 function call PER VERTEX. VBO mode: 1 function call for THOUSANDS of vertices. This is why modern OpenGL is 10-100x faster.

What is Ray Tracing?

⚡ The Physics of Ray Tracing

Ray tracing simulates light transport by following individual light rays backwards from the camera. This is called backward ray tracing or eye tracing:

  1. Cast a ray from the camera through each pixel
  2. Find the first object the ray hits
  3. At the hit point, compute lighting by casting shadow rays to each light
  4. Cast reflection/refraction rays for mirror/glass materials
  5. Recursively combine colors

Why backward? Most light rays from sources never reach the camera. By tracing from the camera, we only compute rays that matter — dramatically reducing computation.

Ray Equation: P(t) = Origin + t × Direction, where t ≥ 0

Ray-Sphere Intersection

📐 Mathematical Derivation

A sphere with center C and radius r is defined by: |P - C|² = r²

Substitute ray equation: |O + tD - C|² = r²

Let OC = O - C. Then: |tD + OC|² = r²

Expand: t²(D·D) + 2t(D·OC) + (OC·OC - r²) = 0

This is a quadratic equation: at² + bt + c = 0

Where: a = D·D = 1 (if D is normalized), b = 2(D·OC), c = OC·OC - r²

Discriminant: Δ = b² - 4ac. If Δ < 0: no intersection. If Δ ≥ 0: t = (-b ± √Δ) / 2a

We want the smallest positive t (closest intersection).

struct Material {
    Vec3 albedo;       // Base color
    float metallic;    // 0 = dielectric, 1 = metal
    float roughness;   // 0 = mirror, 1 = diffuse
    float emission;    // Self-illumination strength
    float ior;         // Index of refraction (glass ~1.5)

// ─── Sphere ───
struct Sphere {
    Vec3 center;
    float radius;
    Material mat;

    // Returns t (distance along ray) if hit, -1 if miss
    float hit(const Ray& ray) const {
        Vec3 oc = ray.origin - center;
        float a = ray.direction.dot(ray.direction);  // = 1 if normalized
        float b = 2.0f * oc.dot(ray.direction);
        float c = oc.dot(oc) - radius * radius;
        float discriminant = b*b - 4*a*c;

        if (discriminant < 0) return -1;

        float sqrtDisc = sqrt(discriminant);
        float t = (-b - sqrtDisc) / (2 * a);  // Near intersection
        if (t > 0.001f) return t;

        t = (-b + sqrtDisc) / (2 * a);       // Far intersection
        if (t > 0.001f) return t;

        return -1;
    }
};

std::uniform_real_distribution<float> dist(0, 1);

float randomFloat() { return dist(rng); }

Vec3 randomInUnitSphere() {
    while (true) {
        Vec3 p(randomFloat()*2-1, randomFloat()*2-1, randomFloat()*2-1);
        if (p.dot(p) < 1) return p;
    }
}

// ─── Ray Color (Recursive) ───
Vec3 rayColor(const Ray& ray, int depth) {
    if (depth <= 0) return Vec3(0, 0, 0);

    // Find closest hit
    float closestT = 1e30f;
    const Sphere* hitSphere = nullptr;

    for (const auto& s : scene) {
        float t = s.hit(ray);
        if (t > 0.001f && t < closestT) {
            closestT = t;
            hitSphere = &s;
        }
    }

    if (!hitSphere) {
        // Sky gradient
        float t = 0.5f * (ray.direction.y + 1.0f);
        return Vec3(1.0f, 1.0f, 1.0f) * (1.0f - t) + Vec3(0.5f, 0.7f, 1.0f) * t;
    }

    Vec3 hitPoint = ray.at(closestT);
    Vec3 normal = (hitPoint - hitSphere->center).normalize();
    Vec3 outwardNormal = normal.dot(ray.direction) < 0 ? normal : normal * -1;

    // Emissive material (light source)
    if (hitSphere->mat.emission > 0) {
        return hitSphere->mat.albedo * hitSphere->mat.emission;
    }

    // Diffuse reflection (Lambertian)
    if (hitSphere->mat.metallic < 0.5f) {
        Vec3 target = hitPoint + outwardNormal + randomInUnitSphere();
        Ray scattered(hitPoint + outwardNormal * 0.001f, target - hitPoint);
        return hitSphere->mat.albedo * rayColor(scattered, depth - 1);
    }

    // Metallic reflection
    Vec3 reflected = ray.direction - normal * 2 * ray.direction.dot(normal);
    Ray scattered(hitPoint + outwardNormal * 0.001f, 
                  reflected + randomInUnitSphere() * hitSphere->mat.roughness);
    return hitSphere->mat.albedo * rayColor(scattered, depth - 1);
}

#define IMAGE_WIDTH 800
#define IMAGE_HEIGHT 600
#define SAMPLES_PER_PIXEL 100
#define MAX_DEPTH 50

unsigned char image[IMAGE_HEIGHT][IMAGE_WIDTH][3];

void render() {
    Vec3 cameraPos(0, 2, 8);
    Vec3 lookAt(0, 0, 0);
    Vec3 up(0, 1, 0);

    float viewportHeight = 2.0f;
    float viewportWidth = viewportHeight * (float)IMAGE_WIDTH / IMAGE_HEIGHT;

    Vec3 w = (cameraPos - lookAt).normalize();
    Vec3 u = cross(up, w).normalize();
    Vec3 v = cross(w, u);

    Vec3 lowerLeft = cameraPos - u*(viewportWidth/2) - v*(viewportHeight/2) - w;
    Vec3 horizontal = u * viewportWidth;
    Vec3 vertical = v * viewportHeight;

    for (int j = 0; j < IMAGE_HEIGHT; j++) {
        for (int i = 0; i < IMAGE_WIDTH; i++) {
            Vec3 color(0, 0, 0);

            // Anti-aliasing: multiple samples per pixel
            for (int s = 0; s < SAMPLES_PER_PIXEL; s++) {
                float uu = (float)(i + randomFloat()) / (IMAGE_WIDTH - 1);
                float vv = (float)(j + randomFloat()) / (IMAGE_HEIGHT - 1);

                Vec3 dir = lowerLeft + horizontal * uu + vertical * vv - cameraPos;
                Ray ray(cameraPos, dir);
                color = color + rayColor(ray, MAX_DEPTH);
            }

            // Average samples and gamma correct (sqrt for gamma 2.0)
            float scale = 1.0f / SAMPLES_PER_PIXEL;
            float r = sqrt(color.x * scale);
            float g = sqrt(color.y * scale);
            float b = sqrt(color.z * scale);

            // Clamp and convert to byte
            image[j][i][0] = (unsigned char)(fmin(r, 1.0f) * 255.99f);
            image[j][i][1] = (unsigned char)(fmin(g, 1.0f) * 255.99f);
            image[j][i][2] = (unsigned char)(fmin(b, 1.0f) * 255.99f);
        }
    }
}

void display() {
    glClear(GL_COLOR_BUFFER_BIT);
    glDrawPixels(IMAGE_WIDTH, IMAGE_HEIGHT, GL_RGB, GL_UNSIGNED_BYTE, image);
    glutSwapBuffers();
}

Particle Physics

⚡ Particle Motion Equations

Each particle follows Newton's laws of motion:

Position(t+Δt) = Position(t) + Velocity(t) × Δt
Velocity(t+Δt) = Velocity(t) + Acceleration × Δt

For gravity: Acceleration = (0, -9.8, 0) m/s²

For drag: Acceleration += -k × Velocity (air resistance)

For wind: Acceleration += WindForce / mass

C++ - Particle System
#include <GL/freeglut.h>
#include <math.h>
#include <stdlib.h>

#define MAX_PARTICLES 10000

struct Particle {
    float x, y, z;       // Position
    float vx, vy, vz;    // Velocity
    float r, g, b, a;    // Color (RGBA)
    float size;          // Size in pixels
    float life;          // Remaining life (0 = dead)
    float maxLife;       // Initial life for fade calculation
};

Particle particles[MAX_PARTICLES];
int activeParticles = 0;

// ─── Emitter Configuration ───
struct Emitter {
    float x, y, z;           // Spawn position
    float spawnRate;         // Particles per second
    float minLife, maxLife;  // Life range
    float minSize, maxSize;  // Size range
    float spread;            // Velocity randomness
    float speed;             // Base emission speed
    float gravity;           // Gravity strength
    float drag;              // Air resistance (0-1)
};

Emitter fireEmitter = {
    0, 0, 0,           // Position
    500,                // 500 particles/sec
    0.5f, 2.0f,         // Life 0.5-2 seconds
    2.0f, 8.0f,         // Size 2-8 pixels
    0.5f,               // Spread
    3.0f,               // Upward speed
    2.0f,               // Light gravity
    0.98f               // Slight drag
};

float randomFloat(float min, float max) {
    return min + (float)rand() / RAND_MAX * (max - min);
}

void spawnParticle(const Emitter& e) {
    if (activeParticles >= MAX_PARTICLES) return;

    Particle& p = particles[activeParticles++];

    // Spawn at emitter position with slight random offset
    p.x = e.x + randomFloat(-0.2f, 0.2f);
    p.y = e.y + randomFloat(-0.1f, 0.1f);
    p.z = e.z + randomFloat(-0.2f, 0.2f);

    // Random velocity with upward bias
    p.vx = randomFloat(-e.spread, e.spread);
    p.vy = e.speed + randomFloat(0, e.spread);
    p.vz = randomFloat(-e.spread, e.spread);

    // Fire color gradient: yellow → orange → red → gray
    float t = randomFloat(0, 1);
    if (t < 0.3f) {       // Yellow core
        p.r = 1.0f; p.g = 0.9f; p.b = 0.2f;
    } else if (t < 0.6f) { // Orange
        p.r = 1.0f; p.g = 0.5f; p.b = 0.0f;
    } else if (t < 0.9f) { // Red
        p.r = 0.8f; p.g = 0.1f; p.b = 0.0f;
    } else {               // Smoke gray
        p.r = 0.3f; p.g = 0.3f; p.b = 0.3f;
    }

    p.a = 1.0f;
    p.size = randomFloat(e.minSize, e.maxSize);
    p.maxLife = p.life = randomFloat(e.minLife, e.maxLife);
}

void updateParticles(float dt) {
    // Spawn new particles
    int toSpawn = (int)(fireEmitter.spawnRate * dt);
    for (int i = 0; i < toSpawn; i++) spawnParticle(fireEmitter);

    // Update existing particles
    int writeIdx = 0;
    for (int i = 0; i < activeParticles; i++) {
        Particle& p = particles[i];

        // Apply physics
        p.vy -= fireEmitter.gravity * dt;        // Gravity
        p.vx *= fireEmitter.drag;                  // Drag X
        p.vy *= fireEmitter.drag;                  // Drag Y
        p.vz *= fireEmitter.drag;                  // Drag Z

        p.x += p.vx * dt;
        p.y += p.vy * dt;
        p.z += p.vz * dt;

        // Age and fade
        p.life -= dt;
        float lifeRatio = p.life / p.maxLife;
        p.a = lifeRatio;                           // Fade out
        p.size *= (1.0f + dt * 0.5f);            // Grow over time

        // Color shift: fire cools from yellow to red to gray
        if (lifeRatio < 0.3f) {
            p.r = 0.3f; p.g = 0.3f; p.b = 0.3f;  // Smoke
        } else if (lifeRatio < 0.6f) {
            p.r = 0.8f; p.g = 0.1f; p.b = 0.0f;  // Red
        }

        // Keep alive particles
        if (p.life > 0 && p.y > -5) {
            particles[writeIdx++] = p;
        }
    }
    activeParticles = writeIdx;
}

void drawParticles() {
    // Enable blending for transparency
    glEnable(GL_BLEND);
    glBlendFunc(GL_SRC_ALPHA, GL_ONE);  // Additive blending for glow
    glDepthMask(GL_FALSE);             // Don't write to depth buffer
    glDisable(GL_LIGHTING);

    // Draw as point sprites (GPU handles billboard)
    glEnable(GL_POINT_SMOOTH);
    glEnable(GL_POINT_SPRITE);

    glBegin(GL_POINTS);
    for (int i = 0; i < activeParticles; i++) {
        const Particle& p = particles[i];
        glColor4f(p.r, p.g, p.b, p.a);
        glPointSize(p.size);
        glVertex3f(p.x, p.y, p.z);
    }
    glEnd();

    // Restore state
    glDepthMask(GL_TRUE);
    glDisable(GL_BLEND);
    glDisable(GL_POINT_SPRITE);
    glEnable(GL_LIGHTING);
}

void display() {
    glClear(GL_COLOR_BUFFER_BIT | GL_DEPTH_BUFFER_BIT);
    glLoadIdentity();
    gluLookAt(0, 5, 15, 0, 2, 0, 0, 1, 0);

    // Draw ground
    glColor3f(0.2f, 0.2f, 0.2f);
    glBegin(GL_QUADS);
        glVertex3f(-10, 0, -10);
        glVertex3f( 10, 0, -10);
        glVertex3f( 10, 0,  10);
        glVertex3f(-10, 0,  10);
    glEnd();

    drawParticles();
    glutSwapBuffers();
}

void update(int value) {
    static int lastTime = 0;

    float dt = (currentTime - lastTime) / 1000.0f;
    lastTime = currentTime;

    glutPostRedisplay();

}

Debugging & Common Errors

Graphics programming is notoriously difficult to debug. This guide covers the most common FreeGLUT and OpenGL errors and how to fix them.

FreeGLUT Specific Errors

"freeglut (program): ERROR: Function called with no current window defined."

Cause: You called a FreeGLUT function that requires a current window (like glutPostRedisplay) before creating a window or after destroying the current window.

Fix: Call glutCreateWindow first, or use glutSetWindow(id) to set a valid window before the call.

"freeglut (program): ERROR: Function called before glutInit."

Cause: Any FreeGLUT function (except glutInitErrorFunc and glutInitWarningFunc) called before glutInit.

Fix: Ensure glutInit(&argc, argv) is the FIRST FreeGLUT call in main().

"freeglut (program): WARNING: Display mode '...' is not supported."

Cause: Your GPU/driver doesn't support the requested display mode (e.g., GLUT_STEREO on a non-3D display).

Fix: Check available modes with glutGet(GLUT_DISPLAY_MODE_POSSIBLE) or use fallback modes.

  4. Is depth testing enabled but Z values wrong? Try glDisable(GL_DEPTH_TEST) temporarily.
  5. Is the clear color the same as your object color? Try glClearColor(1,0,0,1) to see if anything renders.
  6. Are you in the right matrix mode? glMatrixMode(GL_MODELVIEW) for objects, GL_PROJECTION for camera.
  7. Is the viewport set correctly? Call glViewport(0,0,w,h) in reshape.

Flickering / Tearing

⚠️ Causes:
  • No double buffering: Ensure glutInitDisplayMode(GLUT_DOUBLE) and glutSwapBuffers()
  • V-Sync off: Call glutSwapInterval(1) to enable V-Sync
  • Drawing outside display callback: Only render from glutDisplayFunc callback
  • Multiple buffer swaps per frame: Call glutSwapBuffers() exactly once per frame

Graphics Glossary

Complete terminology reference for computer graphics.

TermDefinition
AliasingJagged edges or moiré patterns caused by insufficient sampling. Anti-aliasing techniques (MSAA, FXAA) reduce this.
AlphaThe transparency channel (A in RGBA). 0 = fully transparent, 1 = fully opaque.
Ambient LightConstant illumination that simulates indirect light bouncing in a scene. Not physically accurate but computationally cheap.
Backface CullingSkipping rendering of polygons facing away from the camera. Improves performance by ~50% for closed meshes.
Barycentric CoordinatesA coordinate system for triangles where any point P = αA + βB + γC with α+β+γ=1. Used for interpolation in rasterization.
BillboardA quad that always faces the camera. Used for particles, trees, and sprites.
BlendingCombining the color of a new fragment with the existing framebuffer color. Used for transparency and glow effects.
BufferA region of GPU memory used to store data (vertices, indices, pixels, etc.).
ClippingRemoving geometry that falls outside the view frustum. Performed by fixed-function hardware.
Depth Buffer (Z-Buffer)A per-pixel storage of depth values. Used for hidden surface removal (objects behind others are not drawn).
Diffuse ReflectionLight scattered equally in all directions by a rough surface. Follows Lambert's cosine law.
Display ListA pre-compiled sequence of OpenGL commands. Deprecated in modern OpenGL; use VBOs instead.
Double BufferingUsing two framebuffers: one for rendering (back), one for display (front). Swapped via pointer exchange to prevent tearing.
FragmentA potential pixel generated by the rasterizer. May be discarded by depth/stencil tests before becoming a pixel.
Fragment ShaderA GPU program that determines the final color of each fragment. Runs once per fragment.
FrameA single complete image rendered to the screen. At 60 FPS, 60 frames are displayed per second.
FramebufferThe collection of buffers (color, depth, stencil) that hold the final image data.
FrustumThe pyramid-shaped view volume defined by the camera's field of view and clip planes.
G-BufferMultiple render targets storing intermediate data (position, normal, albedo) for deferred shading.
Gamma CorrectionConverting linear light values to non-linear display values (approximately x^(1/2.2)). Monitors expect sRGB input.
Geometry ShaderA shader stage that can generate or destroy primitives (points, lines, triangles) on the GPU.
GLSLOpenGL Shading Language. C-like language for writing vertex, fragment, and geometry shaders.
Homogeneous CoordinatesRepresenting 3D points as 4D vectors (x,y,z,w). Allows translation to be expressed as matrix multiplication.
Immediate ModeLegacy OpenGL rendering where each vertex is sent individually via glVertex*. Very slow; use VBOs instead.
Index BufferA buffer storing vertex indices, allowing shared vertices between triangles. Reduces memory usage.
InterpolationComputing intermediate values between known data points. GPUs interpolate vertex attributes across triangles.
Level of Detail (LOD)Using simpler geometry for distant objects to improve performance without noticeable quality loss.
MatrixA rectangular array of numbers used to represent linear transformations (rotation, scale, translation).
MipmapPre-computed smaller versions of a texture. Used for high-quality minification filtering.
Model-View-Projection (MVP)The three matrices that transform vertices from object space to screen space: Model × View × Projection.
NormalA vector perpendicular to a surface. Used in lighting calculations to determine surface orientation.
Normal MapA texture storing surface normals per-texel, allowing detailed lighting without extra geometry.
Orthographic ProjectionA projection where parallel lines remain parallel. Used for 2D games, CAD, and UI.
Per-Pixel LightingComputing lighting in the fragment shader for each pixel, rather than per-vertex. More accurate but slower.
Perspective ProjectionA projection where distant objects appear smaller. Mimics human vision.
PixelThe smallest addressable element of a digital image. Short for "picture element."
RasterizationThe process of converting vector graphics (triangles) into raster images (pixels). Performed by fixed-function GPU hardware.
Render TargetA texture or buffer that receives rendering output. Multiple render targets allow deferred shading.
ShaderA GPU program that processes vertices, fragments, or geometry. Replaces fixed-function pipeline stages.
ShadingThe process of determining the color of a surface based on lighting, material properties, and view direction.
Shadow MapA depth texture rendered from the light's perspective, used to determine which pixels are in shadow.
Specular ReflectionMirror-like reflection where light bounces at the same angle as incidence. Creates highlights on shiny surfaces.
Stencil BufferA per-pixel mask (typically 8 bits) used for advanced effects like outlines, shadows, and reflections.
TexelA texture pixel. The smallest unit of a texture map.
TextureAn image applied to 3D surfaces to add detail without increasing geometry complexity.
Texture AtlasA single large texture containing multiple smaller textures. Reduces texture binding overhead.
Texture Coordinates (UV)2D coordinates (u,v) that map vertices to positions on a texture. Range [0,1] typically.
TransformationChanging the position, orientation, or scale of an object using matrices.
TriangleThe fundamental rendering primitive. All 3D models are composed of triangles.
UniformA shader variable that is constant for all vertices/fragments in a draw call (e.g., transformation matrices).
VAO (Vertex Array Object)An OpenGL object that stores vertex attribute configuration. Binds all vertex data with one call.
VBO (Vertex Buffer Object)A GPU buffer storing vertex data (positions, normals, colors, UVs). Uploaded once, rendered many times.
VectorA mathematical object with magnitude and direction. In graphics, used for positions, directions, and colors.
VertexA point in 3D space with associated attributes (position, normal, color, UV).
Vertex ShaderA GPU program that processes each vertex. Typically transforms vertex positions and passes attributes to the fragment shader.
View Frustum CullingSkipping objects entirely outside the camera's view frustum. Major performance optimization.
ViewportThe rectangular region of the window where rendering occurs. Defined by glViewport.
V-SyncVertical synchronization. Waits for the display's refresh cycle before swapping buffers. Eliminates tearing but may cause input lag.
WireframeRendering mode where only polygon edges are drawn. Useful for debugging geometry.
Z-FightingVisual artifacts where two surfaces are at nearly the same depth, causing the depth buffer to flicker between them.
